# Server Vault 的文件系统、持久化历史与 CRDT 协调

日期：2026-10-04。调查与 spike 固定 Loro 1.16.2、redb 4.3.0、notify 8.2.0，在 Linux 上验证。本文记录完整实现方案、正确性边界和实验结果；配置示例标明目标契约，不引用外部可变文档。

## 方案概要

server 为每个配置的 Vault 运行一个 host VaultInstance，持有独立 EditorCore、物理目录 Backend、私有历史存储和文件监听。客户端通过对应 Vault URL 加入同一历史。普通文件可由其他编辑器修改，server 将确认读到的磁盘变化转换成 CRDT 操作，与已接受的协作编辑合并。

每份文档同时维护当前 CRDT 状态、可恢复的持久化历史，以及“磁盘字节对应哪个历史版本”的基线。编辑 / 同步先提交历史，保存再写回普通文件；磁盘基线可以落后于当前正文。连续外部修改沿磁盘基线分支演进，再合入当前 core。

正式 host 默认持久化。重启恢复同一份身份、历史和磁盘基线；首次导入与显式重置才建立新历史。每个 Vault 配置自己的物理目录与状态目录，统一声明在 server 的 `config.toml` 中。第一个协作里程碑仅支持在线打开与编辑，客户端每次连接从 host 快照建立活动历史。

正确性针对已确认的快照序列。普通文件通知不能恢复未读取的中间状态，也没有通用的跨资源事务、跨程序 CAS 或外部保存完成证明。不确定状态保留材料并停止自动协调。首期完成主动核对、连续分支导入与可靠回执，保留显式保存；自动投影写回单独验证。

## 1. Server 与每个 Vault 的配置

一个 server 配置文件中，每个 `[[vaults]]` 条目描述一个 hosted Vault。监听地址、来源与认证属于 server；物理目录、只读策略与持久化状态属于具体 Vault，无需为每个 Vault 再拆一个 TOML 文件。

以下是**目标配置契约**：

```toml
[server]
listen = "127.0.0.1:7437"
allowed_origins = ["http://localhost:1420", "http://127.0.0.1:1420"]
# token_env = "CELESTITE_TOKEN"
# web_dir = "./web/dist"

[[vaults]]
id = "notist"
name = "notist docs"
path = "../notist/docs"
state_dir = "./state/notist"
read_only = false

[[vaults]]
id = "notes"
name = "笔记"
path = "./notes"
state_dir = "./state/notes"
read_only = false
```

`notist` 的连接地址为 `http://127.0.0.1:7437/api/v1/vaults/notist`。每份状态目录容纳该 Vault 的数据库，例如 `history.redb`，以及必要的恢复材料；内部文件命名由存储实现管理。

配置规则：

- 相对路径以配置文件所在目录为基准。命令行覆盖的相对路径以当前工作目录为基准，并对应到明确的 Vault ID。
- `id` 是 URL 使用的配置标识，持久化的 Vault / 文档 / history 身份存储在 profile 内。更改显示名称不会创建新历史；更改 URL 标识、保留同一 profile 时应保持逻辑身份。
- 正式 host 的每个 Vault 都有明确、稳定的 `state_dir`。纯内存模式作为显式临时运行能力，不能成为正常 host 启动的隐式回退。
- Vault 根目录、状态目录和静态资源目录按实际路径校验。状态目录不能位于任何 hosted Vault 内，状态目录之间也不能重叠；同一 profile 只能由一个 host owner 打开。
- `read_only` 限制客户端编辑与文件写回。host 仍可读取外部变化、更新自己的历史和基线、向客户端提供更新；状态目录仍需要写权限。
- profile 与逻辑身份、物理根目录绑定。配置到别的目录、移动 profile 或恢复备份需要明确的迁移校验，不能把不同目录静默接入已有历史。

### 状态目录的布局选择

首期将状态目录放在 Vault 外部，让普通文件树和 watcher 只接触用户文件。内部数据库写入不会变成 Vault 文件事件，也不会进入用户文本 CRDT。

Vault 内 `.celestite/` 可作为后续布局选项，便于目录与历史一起迁移；接入前需要保留命名空间、完整排除监听 / 文件 API / Catalog、定义备份与 owner 锁。内部布局不影响历史必须持久化这一要求。

2026-10-04 的现有 server 仍使用 `[server].state_dir`，在其下按配置 ID 创建 `<id>.redb`；尚不接受上例 `[[vaults]].state_dir`。当时的 `just serve-notist` 未指定状态目录，使用内存历史。迁移时为各 Vault 指定原数据库所在 profile 或显式迁移文件，保留内部身份与日志，不能因文件名 / 布局变化重新 seed。

## 2. 首次导入、持久化与重启

### 首次初始化

首次初始化创建 Vault 身份、历史身份和 host 实例身份。按需登记可编辑文件：读取当时确认的磁盘内容，创建文档身份与初始 CRDT 状态，记录种子快照及磁盘基线，并提交到私有历史库。文件树扫描与新文件登记需要对应的目录协调；文本历史不会凭空包含初始化之前的文件修改。

这一步是从现有正文建立新历史。即使文本相同，两次独立初始化也可能产生不同字符身份，不能把它们当作同一篇 CRDT 文档。

首次初始化与正常启动采用不同语义：创建新 profile 是明确的服务端初始化操作；正常启动打开已初始化的 profile。已有 host 的状态丢失、损坏或不匹配时报告错误，不能静默从普通文件重建一份历史继续服务。显式重置才创建新身份 / 历史，并要求旧客户端重新加入。

### 必须持久化的状态

| 范围         | 持久状态                                                               |
| ------------ | ---------------------------------------------------------------------- |
| Vault / 实例 | Vault 身份、history 身份、host 实例身份、schema、目录绑定及 owner 信息 |
| 文档         | 文档身份、路径、种子 / checkpoint、操作 journal、已提交因果版本        |
| 同步         | 已确认接收的 pending 依赖包、重试去重与回执所需信息                    |
| 文件投影     | DiskCursor、写回意图、回执、未解决的故障证据                           |
| 目录协调     | 已实现目录操作的恢复意图；后续 Catalog 的身份与状态                    |

CRDT 历史持久化与普通文件保存是两次不同提交。历史已持久化的正文仍可以尚未写入 `.md`；客户端回执必须区分 host 已接受、历史已持久化和普通文件已保存。

CRDT 历史不是个人 undo 会话。恢复正文与同步身份，不意味着恢复所有视图的撤销分组、选区和 redo 栈。writer 的操作身份与 VaultInstance 身份也分开，重启不能在有并发风险时复用 writer / counter。

### 正常重启

1. 验证配置和目录关系，独占打开每个 Vault 的 profile，检查 schema、身份及根目录绑定。
2. 从 checkpoint / seed 和 journal 恢复已提交 CRDT 状态，重建 pending 依赖与恢复材料。
3. 恢复目录操作和文件写回；遇到不确定状态，仅冻结受影响文档并保留证据。
4. 启动 watcher 并进行初始核对，按恢复后的 DiskCursor 处理停机期间的磁盘变化；扫描结束后补处理其间到达的通知。
5. 对正常文档开放服务，首期客户端重连时从 host 快照重建会话，随后按版本增量同步；后续启动 / 周期 / 溢出扫描弥补通知缺失。

初始化扫描不假定整库是一个原子快照。已登记文档逐份协调；暂停的文档明确报告恢复状态。数据丢失或损坏导致某个 Vault 无法恢复时，该 Vault 不提供看似正常的新历史。

没有历史持久化时，重启会丢失 host 未写回的编辑、旧字符身份、磁盘对应版本和恢复意图。旧客户端操作属于另一份历史，不能仅因为路径 / 内容一致就导入。这只适合临时测试。

profile 应支持 checkpoint 和 journal 压缩，保留 DiskCursor、待恢复意图和同步协议要求的历史范围。普通文件不是私有历史库的备份替代品；迁移 / 备份要同时保留所需状态及用户文件。当前根目录绑定需显式迁移，不能靠改 TOML 路径绕过校验。

### 第一个里程碑：单 host 在线协作

客户端只在已验证的在线会话中打开远端 Vault / 文档并接受编辑。离线不能依靠缓存重新打开远端 Vault，不能打开新的远端文档；已打开视图停止编辑，可显示只读内容并保留恢复材料。连接失败、请求超时或权限失效时暂停新操作，UI 与 core 同时限制编辑。网络失效到被检测之间仍有窗口，必须处理这段时间的待确认输入。

每次连接和重连均采用 host 的当前历史重建活动 core，分配新 writer，开始新的个人 undo 会话。客户端会话缓存可以替换；首期不把它当作跨会话的离线 CRDT 副本，不自动重放旧会话更新。默认 OPFS 独立 Vault 继续本地编辑，host 自身的本机编辑不受远端 client 是否在线影响。

连接流程：

1. 在旧会话停止新操作，把尚未获得 host 持久化确认的操作、对应身份及待确认 UI 输入保存为独立恢复材料。
2. 验证协议、Vault / 文档历史身份与权限，建立新的会话代次。历史身份改变时先提示，再加入 host 当前历史；不同历史的旧包不导入。
3. 获取 host 快照，创建活动 core，替换可丢弃缓存，并补齐快照与订阅之间的更新。
4. host 确认会话可写且初始同步完成后开放编辑；所有后续包与回复绑定会话。host 校验尚未提交操作的会话有效性，客户端丢弃旧会话的迟到回复。
5. 在原历史身份相同的条件下，按操作身份与 host 持久化版本核对恢复材料。已持久化的操作可以清理；其余保留供比较、导出或显式生成新的恢复编辑。

请求超时不能推断为提交失败。即使不支持离线编辑，断线瞬间的本地编辑也可能尚未发送，或已提交但丢失回执。因此“以 host 为准”只直接替换活动缓存，未确认修改先隔离保留。恢复材料用于处理故障，不开放断线后的新编辑，也不构成自动离线同步。

| 连接校验结果                  | 首期处理                                                           |
| ----------------------------- | ------------------------------------------------------------------ |
| 同一历史、版本落后或并发      | 正常同步；新连接从 host 快照开始，会话内交换增量                   |
| Vault / 文档历史身份改变      | 提示远端历史改变，采用新活动会话，保留旧恢复材料                   |
| host 缺少它曾确认持久化的操作 | 提示可能发生回滚并保留材料，新会话采用 host 快照，不自动补回旧操作 |
| 权限或协议不允许编辑          | 拒绝编辑，不发送旧操作                                             |

身份校验在连接时进行，并在每个文档导入及会话变化时继续执行。URL 只用于定位，不能证明仍是同一 Vault。不同因果版本本身不是异常，不能把正常落后或并发误报为历史不一致。

首期集中验证在线收敛、个人撤销、文件系统导入、host 持久化、显式保存及连接故障。持久化离线副本、离线正文编辑与目录离线操作后续独立设计。普通网络断线时已打开视图可只读保留；首次或离线重新打开仍要求 host 可用。

## 3. 输入语义

物理事件是核对提示，不能直接解释成文本操作。事件可能合并、重复、延迟或丢失；旧事件处理时只能读到当前内容，无法读取那个事件发生时的内容。丢失通知通过启动扫描、失败后重新扫描和周期扫描补足最终状态。

令 D0、D1、D2… 为协调器先后确认并提交的文件快照。每个外部修改定义为确定的 edit script：

    Ei = Diff(Normalize(Di-1), Normalize(Di))

这允许外部编辑器基于旧 buffer 覆盖文件：若它移除了已经确认写入磁盘的修改，Ei 就包含相应删除。协议不推测用户意图。

必须区分“前一个确认的快照”与“前一个实际物理状态”。如果文件经历 A → B → A，而只读到了 A，无法知道 B。漏读中间状态不保证与逐次观察等价，连最终可见的合并正文也可能不同。

复现反例：初始磁盘 `a`；core 并发把 `a` 改成 `X`；外部将磁盘清空再写回 `a`。逐次观察生成删除旧字符和插入新字符，合并为 `Xa`；只读最后的 `a` 则没有外部变化，正文为 `X`。这两条观察序列各自确定，信息不足以让它们相同。

读取过程也需要契约。原地写入可能暂时产生空正文、合法 UTF-8 的半成品或读到混合内容。两次内容和 metadata 相同、等待安静窗口，都只能降低误读概率，不能证明另一个进程不会继续写。严格完整保存语义需要外部采用原子替换或参与协作协议。普通模式将已接受的有效快照解释为状态变化，非法 / 不稳定读取延迟处理，不把读错误当成清空正文。

## 4. 核心状态与不变量

每份文档持有：

| 状态              | 内容                                                                                           |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| C                 | 当前已接受的 CRDT 正文与完整历史                                                               |
| P：DiskCursor     | 文档 / 历史身份、观察序号、因果版本及 frontiers、对应正文、原始字节哈希、编码 / BOM / 换行格式 |
| W：WriteIntent    | 写回 ID、阶段、预期磁盘哈希、目标原始字节和哈希、目标正文及因果版本                            |
| U：UncertainWrite | 无法确定写回是否发生时保留的 P、W、当前读到的字节和错误证据                                    |

原始字节或可恢复的内容地址引用用于证据与恢复；生产格式应避免在每个日志项重复保存完整正文。

必须保持以下关系：

1. 从 C 的历史恢复到 P.version，得到 P.text，保留原有字符身份。
2. Normalize(P.bytes) = P.text，Hash(P.bytes) = P.hash。混合换行的原始字节可以与重新编码结果不同。
3. P.version 是 C 中已具备的历史状态，不包含 C 的全部最新操作也完全合法。
4. 每个外部观察的操作与新 P 一起原子提交；任何客户端发布均在提交之后。
5. W 的目标版本确实对应目标正文和编码字节，不能指向提交期间的最新正文。
6. 已处理的相同字节不会生成新编辑。相同正文、不同字节格式只更新 P 的物理信息。
7. 待恢复 W 阻止普通核对和后续写回，避免给未知磁盘状态指定历史版本。

相同字节可对应不同历史版本；哈希只能验证内容，不能反推因果版本。P.version 是协调器记录的关联。历史压缩必须保留 P、W 和未解决分支所需的历史，不能裁掉还需要 fork 的状态。

## 5. 一次外部观察的算法

所有生产文件访问仍通过受限 Backend 路径 / 目录句柄，保持文档 ID、历史 ID 和只读权限的校验。

1. 没有待恢复写回时，读取候选字节，校验大小、UTF-8 / 二进制内容和文件身份。
2. 若字节哈希等于 P.hash，结束，不生成新 operation。
3. 从 P.frontiers 创建完整历史分支 F；为它分配新的唯一 writer。
4. 在 F 上把 P.text 更新为 Normalize(D)，得到版本 Vf 和操作包 E。仅格式改变时 E 为空。
5. 在隔离 trial 上验证 E 合入当前 C 后的正文、大小和历史约束，避免错误或 diff 超时污染 live core。
6. 原子提交 E 的 journal、新的 P=(D,Vf)、序号和必要的恢复证据。
7. 对 live core 应用同一份 E，发布正文 / 历史变更与回执。

第 7 步失败时，应停止这个运行实例并从已提交状态重建，不能在旧 live 状态继续处理新请求。生产实现可以维护待提交 trial，但 UI 和网络在提交成功前不得把它视为已接受的编辑。

记录新的 P 时使用 **Vf**，不能使用 C 合并后的版本 Vm。磁盘只有分支正文 D，未包含其他并发编辑。

连续观察 D1 → D2 时，从 D1 的 Vf1 继续 fork；该分支继承第一个外部操作，却不继承 core 尚未投影到磁盘的修改。用归纳法可得，每个新分支的可见正文都是对应的 Di，而主 core 持续合并 Ei。重复与乱序网络传输只重放相同操作身份。

后台 diff 必须绑定文档身份、P 的观察序号和任务 ID。完成时检查基线是否仍然适用。core 的协作编辑可以在计算期间推进，E 仍合入最新 C；若磁盘 cursor 已推进，旧任务必须重算或取消。每份文档同时只有一项外部观察在提交，后续通知只安排下一轮核对。

### Diff 选择

不能把编辑器显示用的最长公共前后缀单区间替换直接用于外部分支。

实际反例：

    基线：A middle B
    协作：A MIDDLE B
    外部：A1 middle B1

外部只修改两端。单区间替换却重新创建了中间 `middle`，合并得到 `A1 middle B1MIDDLE`。Loro 1.16.2 的 scalar Myers 更新在实验中得到 `A1 MIDDLE B1`，保留中间字符身份。

生产需要固定算法和 tie-breaking。较大文本先做行级定位、再在变化区做 scalar diff，保留匹配的未变化区域；不能把整行替换直接当作行内的最细编辑。超过资源预算时挂起 / 显示协调失败，不悄悄改成全量替换。超时只停止任务，不能依据计时随机切换为另一种 edit script。重复文本的匹配仍有歧义，确定性不等于还原原编辑器的操作意图。

## 6. 写回与自激

C 的普通文件投影定义为 Encode(C.text, P.format)。写回固定一个目标版本 Vw，新的编辑不能偷偷改变正在写入的目标。

1. 核对当前磁盘并完成之前的观察。
2. 正文与 P.text 相同则不写文件。因果版本不同本身不会触发物理写入。
3. 持久化 W=Prepared，其中包含预期哈希、目标字节和 Vw。
4. 再核对磁盘前提，持久化 W=Started。Prepared 阶段严格禁止物理修改。
5. 暂存并同步目标文件，执行平台提供的替换操作；其条件检查强度必须明确。
6. 已知写入完成后，原子提交 P=目标(Vw)、写回回执并清除 W。
7. 再安排一次磁盘核对，捕获写回之后的外部变化。

同一文档的观察与写回串行。自己的文件通知会在回执之后处理，若磁盘仍是目标，哈希相同，不产生 E。不能靠 origin 字符串、短时忽略 watcher 或时间窗口作为去重依据。

证明固定点：外部及网络最终停止产生新变化、所有已提交观察处理完成、没有未解决写回故障时，C 固定。至多再投影一次固定正文；P 的字节与磁盘一致，随后所有重复通知为空操作，保存也为空操作。归一化 / 编码策略固定，字节哈希记录实际写入目标，避免换行转换产生回环。

这个证明不保证两套外部 formatter 不会反复互改，也不保证任意精确计时内系统停止。那属于持续存在的外部输入。

还需避免网络层空转：重复包仍按 operation ID 去重；没有新增已应用历史、没有新的 pending 依赖时，不追加空 journal、不重复发布变更。依赖尚未齐的包需要持久化并按包身份去重，不能仅凭“可见正文没变”丢弃。原始文件变化通知与已提交的 CRDT 变更通知分开。

## 7. 崩溃恢复与不可判定状态

观察的提交前崩溃：没有发布操作，重读后重新计算安全。提交成功但回执丢失：恢复历史和 P 后，相同字节为空操作；不能生成另一批新 operation 来重试已提交的观察。

写回恢复表：

| 持久状态                                    | 恢复处理                                   |
| ------------------------------------------- | ------------------------------------------ |
| 无 W                                        | 根据已提交 P 进行正常核对                  |
| W=Prepared                                  | 可以证明尚未修改文件；取消或重新核对后重试 |
| W=Started，磁盘等于目标                     | 关联到目标版本，补齐回执                   |
| W=Started，磁盘等于旧基线                   | 不确定，停止自动协调                       |
| W=Started，磁盘是第三份内容 / 不可读 / 缺失 | 不确定，停止自动协调并保留证据             |

旧基线也不安全：`Started → 崩溃且未写入` 与 `Started → 写入目标 → 外部写回旧内容 → 崩溃` 能留下完全相同的数据库与磁盘状态，但后者的实际上一状态是目标。仅凭最终哈希无法选择正确的外部分支。

因此，旧内容不能作为“写回未发生、可以直接重试”的恢复依据。完整 WAL、保留下来的平台提交材料或外部合作协议可以提供额外证据；没有证据时返回 UncertainWrite。

U 状态下提供当前正文、原始磁盘内容、上次基线和写回目标。首期暂停该文档的后续编辑、导入和写回，已提交历史保持可读并可导出。其他文档正常工作。

显式恢复在同一个文档队列内执行：重新读取当前磁盘 D，以当前已提交历史为起点建立与 D 对应的新分支，原子记录这个由用户选择建立的关联并清除旧 W / U。采用磁盘时，该分支作为新正文；保留 core 或手动合并时，在这个关联之后再生成明确的恢复编辑，得到用户选择的正文并保留未保存状态。所有旧历史、目标和故障证据继续保留。后续保存使用新的磁盘基线核对；选择不会被宣称为自动恢复了未知的物理历史。

应用级故障注入能验证上述持久状态机，不能等同于断电验证。文件数据 fsync、目录 fsync、数据库 durability 和平台恢复语义都要纳入真正的断电测试。

## 8. 普通文件系统的写入强度

当前 native 的“内容哈希检查 → 暂存 → rename 替换”不能提供跨程序原子 CAS。确定性实验在检查完成后插入一次外部保存，随后 rename 正常成功，外部内容被覆盖且没有进入历史。再增加一次检查只能缩短窗口。

建议在 Backend 内部明确区分：

- 原子条件替换：有平台 / 协作协议提供真正的条件提交保证。
- 尽力条件替换：哈希核对后替换，仍存在跨程序竞争。
- 不支持：不能提供所需投影能力。

首期主动监听和 CRDT 导入可独立实现；默认保留显式保存和原有冲突检查，不默认启用循环自动写回。显式保存也不因此获得原子 CAS 保证。

### Linux 原子交换的价值与限制

实验还使用 rename exchange：目标暂存文件与真实文件原子交换，真实路径取得目标，私有暂存路径留下被替换版本。即使外部在检查窗口内完成原子保存，也能取得被替换的实际字节，按旧 P 生成 E，再与目标正文的历史合并；被替换的内容不会仅因 rename 消失。

它值得作为后续 Linux 投影实现研究，但不是本次建议直接部署的实现。生产需要把阶段文件身份、目标材料、被替换材料、更新包和回执纳入完整 WAL，保证阶段文件在 journal 确认前保留，并同步目录。

更强限制也已复现：外部仍持有原地写入的旧 FD，exchange 后会继续修改暂存路径下的旧 inode。在读取旧文件后，它还能继续写；提前删除暂存文件会使后续内容不可见。因此 exchange 不能证明任意原地编辑器都已完成保存，也不能提供所有外部行为下的绝对无损。

若要求每次物理变更完整进入 CRDT，需要外部通过 core / 协作 RPC 写入，或使用定义了完整写入边界的受控文件接口。对任意直接修改普通目录的程序，协议只能对确认观察到的有效快照提供严格语义。

## 9. 生产边界与接口

Core 拥有 ProjectionCoordinator：磁盘 cursor、外部分支、journal 原子提交、写回意图、错误状态与恢复决策。Backend 提供真实文件读写、内容版本、平台提交强度和私有历史提交。Watcher 由平台启动，只提交核对提示；它不直接创建 CRDT 操作，也不调用用户编辑的个人 undo 路径。

建议交互面：

    request_reconcile(paths | whole_vault, reason)
    reconcile_document(document_id)
    prepare_projection(document_id, target_version)
    complete_projection(write_id, platform_receipt)
    recover_projection(document_id)
    resolve_uncertain_projection(document_id, explicit_resolution)

内部事务：

    commit_observation(document_id, observation_id,
                       base_cursor_sequence, packet?, new_cursor)
    commit_write_intent(document_id, write_id, intent)
    commit_write_receipt(document_id, write_id, new_cursor)

观察 ID 和 cursor sequence 用于检测重试及过期后台任务；跨实例去重仍使用 CRDT operation ID。生产事务应验证文档身份、旧 cursor sequence 和已有 receipt，不能只做无条件覆盖。更新包、合并后正文和 pending 队列均设置字节与数量预算；超限时拒绝新的输入并明确要求重试 / 快照恢复，不丢弃已经确认接收的依赖包。

异步 diff 在独立计算任务上运行，隔离 trial，完成后通过 actor 检查基线并提交。平台支持稳定读取时利用其能力；不稳定、超过文本上限、非 UTF-8、二进制、文件暂时缺失时保留历史，发布状态，不生成空正文删除。

目录新增、删除、重命名另建 Catalog 协调规则。临时缺失不等于永久删除；同内容哈希不等于同文档身份；已有打开文档不能仅因原子保存更换 inode 就换文档 ID。附件保持二进制文件模型，不走文本 diff。

旧 profile 缺少 saved_version 或无法恢复对应 frontiers 时，不能只用 saved_text 发明一个分支。保持冲突协调，直到显式建立可恢复的磁盘基线；元数据损坏或历史缺失停止自动导入。

## 10. 验证结果与实施顺序

独立实验目录：`spikes/filesystem-crdt`。固定依赖锁文件，脱离生产 workspace，完整 checkpoint / redb 事务作为可执行规格。生产应采用追加 journal，保留现有 live core 和事件 / undo 会话；实验的固定 writer 仅用于可复现测试。

命令：

    CARGO_TARGET_DIR=/home/azurice/Files/.celestite-headless-target \
      cargo test --manifest-path spikes/filesystem-crdt/Cargo.toml -- --nocapture

Linux 上 24 项测试通过，包含：

- 连续外部 diff 与 core 未保存编辑；每次 cursor 仍恢复出对应磁盘正文。
- 三副本乱序、重复更新；正文与因果版本收敛，个人撤销保留外部操作。缺失依赖的包跨重启保留，补齐后应用；重复包不追加提交。
- 观察提交前 / 后崩溃；真实 redb 重开，重复通知不会生成新操作。
- 七个写回崩溃边界；可证明状态自动恢复，不确定状态保留材料并停止。
- 真实 notify 与原子替换；自身写回后 100 次核对 / 保存不生成额外 CRDT 操作或文件写入。
- 编码 / BOM / 换行变化、UTF-8、emoji、组合字符、空正文、无效输入。
- 2,197 组初始与两次后续 Unicode 文本组合；保留无关 host 插入，重排 / 重放后副本收敛。
- 24 个固定随机种子，每个 100 步，合计 2,400 步磁盘变化、漏观察、重复观察、协作编辑、导入与保存交错；每步验证 cursor 不变量，结束后验证收敛和固定点。
- 六类限制反例：粗 diff、未观察的中间状态、非原子 CAS、原地写入的半成品、Started / 旧字节的恢复歧义、exchange 后的旧 FD 写入。

这是有限测试与条件性归纳论证，未对全部输入、操作系统、断电状态做形式化证明，也没有把生产 server 切换到新算法。

实施顺序：

1. Server 将持久化配置归属到每个 Vault；正式 host 要求稳定 profile，区分首次初始化、正常恢复与显式重置。迁移已有数据库并保持身份，开发启动命令也使用固定状态路径。
2. Core 增加可恢复 DiskCursor、历史分支与观察事务；缺少旧基线版本时保留冲突退路，不猜测历史。
3. 加入后台细粒度 diff、任务身份校验、外部 writer、已提交事件和 journal 去重。
4. Server watcher 驱动主动核对，加入启动 / 周期 / 溢出扫描；客户端获取已提交更新。
5. 完善 Prepared / Started / UncertainWrite 状态与回执，保留显式保存，复用相同故障测试。
6. 完成首期在线客户端接入：连接时从 host 快照建立会话，离线禁止打开和编辑，重连替换缓存并保留 / 核对未确认修改；验证历史变化、权限变化与迟到回复。
7. 验证进程重启、停机期间的外部修改、旧客户端重连与路径迁移；单独验证平台写回策略、Linux 材料保留与断电恢复，再决定自动投影范围。
8. 独立推进目录 Catalog、附件与外部稳定身份协调；离线客户端副本和离线编辑在在线协作闭环后设计。
