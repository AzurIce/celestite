# 在线协作与快照 / Patch 离线工作流（Draft）

日期：2026-10-06。状态：Draft，具体设计待定。

本文记录本轮关于在线 CRDT、离线修改与重新合入的讨论。已确定的阶段边界是先不做 CRDT 离线编辑；快照、patch、合并窗口、持久化与 core 拆分等具体设计均待定。下文保留候选方案及其需要满足的约束，供后续设计使用，不表示方案已经采纳或实现，也不替代当前目标架构。不引用外部可变文档。

## 1. 已确定的阶段边界

**本阶段先不做 CRDT 离线编辑。** 离线累积协作 CRDT 操作、重连后自动同步合并的能力留待后续考虑。

这一阶段边界不以快照 / patch 方案落地为前提，也不决定 host 是否继续持久化在线 CRDT 历史。离线工作流及其实施时间另行确定。

## 2. 候选工作流（待定）

在线协作继续由固定 host 管理 Vault，文本通过 CRDT 实时同步。离线工作的一种候选方案是使用普通文件快照和 patch：用户下载一份工作副本，在本地使用任意编辑器修改，再将修改提交回 host。

该候选方案将用户侧操作简化为三个动作：

| 动作       | 输入与产物                                                     |
| ---------- | -------------------------------------------------------------- |
| 下载       | 导出某个确定版本的 Vault 快照及其基线信息                      |
| 更新       | 指定原基线，下载该基线到 host 新快照的 patch，在本地应用或合并 |
| 上传 patch | 提交相对于已知基线的本地修改，由 host 合并、审阅并发布         |

在这一候选方案中，Git 可以用于本地提交、备份、比较和冲突处理。Celestite 的 Vault、存储后端和协作链接无需绑定 Git，也无需提供 Git remote 协议。可以先提供快照下载、更新 patch 下载和 patch 上传入口，再考虑专用 CLI 或一键更新器；具体工具与交互尚未确定。

远端协作会话断线后的交互限制，和用户主动下载普通文件进行离线工作，是两个不同的产品流程。

## 3. 基线与变更方向

| 符号 | 含义                                             |
| ---- | ------------------------------------------------ |
| `B`  | 用户上一次取得的、可恢复内容的 host 基线快照     |
| `L`  | 用户基于 `B` 修改后的本地工作目录                |
| `H`  | 本次更新或合并时捕获的 host 快照；捕获后内容固定 |
| `L'` | 将 host 的更新合入本地修改后的工作目录           |
| `M`  | 在服务端完成合并、冲突处理与审阅后的候选结果     |

更新和提交都可以用 patch 表达，但方向不同：

```text
更新 patch：B -> H
提交 patch：B -> L

本地更新：merge(base=B, local=L, incoming=H) -> L'
服务端合并：merge(base=B, current=H, incoming=L) -> M
```

这里的快照版本标识整个 Vault 的文件状态，与某个文档的 CRDT 因果版本分开。`H` 表示一个确定版本，不能在同一次合并过程中跟着在线协作不断变化。

## 4. 下载：取得一致的工作副本

下载需要返回普通文件内容，以及足以识别和恢复基线的信息，例如 Vault 身份、快照 ID、路径清单和内容摘要。元数据的具体文件名与存放位置尚未确定。

「最新状态」倾向定义为 host 已接受的逻辑状态：已加载文本可以包含尚未写回普通文件的编辑；目录和附件也必须对应这份快照。其他客户端尚未送达 host 的输入不属于该快照。

导出应先捕获不可变快照，再传输或压缩。不能一边遍历持续变化的物理目录，一边把混合了多个时刻的结果称为同一个版本。未加载文件和附件可以按需读取，但需固定内容版本，或在读取时校验并重试。

普通下载不必让所有人进入长时间的合并冻结窗口，也不必隐式保存所有文档。实现可以在短暂的协调边界上固定目录清单、正文版本与附件版本，之后继续在线协作。若首期只支持导出已落盘状态，应明确其范围与时效，避免把它显示为当前实时状态。

离线工作副本需要保留 `B` 的可恢复内容。只有快照 ID 或哈希，无法从本地修改后的 `L` 恢复原文。基线可以来自本地保留的快照、可再次下载的服务端快照，或可覆盖相关内容的 Git 提交；具体保留机制仍待选择。

## 5. 更新：下载 patch，在本地应用或合并

用户以基线 `B` 请求更新，host 捕获新快照 `H`，返回 `B -> H`。不要求每次重新下载整个 Vault。

本地目录仍等于 `B` 时，可以校验后直接应用 patch，得到 `H`。本地已经改成 `L` 时，则需要把远端更新与本地修改合并；文本可能发生冲突，文件删除、重命名和附件替换也可能发生冲突。

标准文本 patch 可以交给 `patch`、`git apply` 或图形化工具处理。直接应用失败后应保留修改并进入人工处理；依赖上下文或模糊匹配的成功，也不等同于正确理解了两侧意图。需要可靠的三方合并时，必须能取得共同基线 `B`。

Git 是一种可选的本地保障方式，可以在应用前记录当前修改，并利用提交保存基线。`git apply --3way` 还要求 patch 具有合适的 blob 身份信息，且本地能取得对应基底 blob；普通下载的 unified diff 并不会自动获得这一能力。

更新成功后，有两个不同结果：

- 工作目录变成包含两侧修改的 `L'`。
- 远端基线推进到 `H`。

下一次提交应生成 `H -> L'`，不能把 `L'` 当成新的远端基线，否则本地尚未提交的修改会被吞进基线。更新失败或冲突尚未处理完成时，基线不能被提前标记为已推进。

## 6. 上传：提交相对于基线的修改

用户上传 `B -> L`，并同时指定其所属 Vault 和基线 `B`。即使 host 已经从 `B` 演进到 `H`，也不要求用户先下载 `H` 才能提交。

host 取得 `B` 的内容后，验证 patch 并重建本地候选内容，再以 `B` 为共同祖先将其与 `H` 合并，生成 `M`。实现可以只恢复受影响路径所需的数据，无须把整个 Vault 同时装入内存。

无冲突部分可以自动合并；冲突需要用户审阅和选择。没有冲突标记只说明工具未发现对应的结构或文本冲突，不能保证引用、程序语义或业务意图正确。

可以为 `M` 提供独立的合并工作区，展示两侧变化和冲突。未来允许多人在这个工作区共同解决冲突时，可以临时使用 CRDT。确认发布时，将审阅结果表达为 Vault 变更集 `H -> M`，无需把合并工作区里的每次输入都作为离线提交历史保留下来。

这里的「合并为一次 Diff」是指表达最终净变化，不意味着可以把一个旧版本的 Diff 无条件写入仍在变化的正式 Vault，也不意味着直接重置正式协作会话的历史。变更仍需经过 host 的统一操作入口，并协调活动文档、目录、附件和客户端状态。

## 7. 合并窗口与发布竞争

本轮讨论过一个候选方案：由客户端发起合并窗口，暂停正式 Vault 的协作写入，立即保存当前状态，取得固定的 `H`，然后上传 patch、处理冲突并确认发布。冻结后的快照可以提供下载链接，但在 host 能恢复 `B` 的前提下，用户不必先下载它。

候选工作流可以简化为下载、更新、上传 patch；是否采用这一工作流，以及是否在整个合并过程中冻结正式 Vault，均待确定。两种发布方式的主要差别是：

| 发布方式                       | 必须满足的条件                                                     | 代价                                                 |
| ------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------- |
| 全程冻结正式 Vault             | 建立写入边界，处理在途输入，保存完成后固定 `H`，合并期间阻止其变化 | 长时间冲突处理会暂停所有人的正式编辑                 |
| 合并工作区独立运行，发布时校验 | 审阅针对固定 `H`；发布时检查当前状态仍符合该版本或明确的前置条件   | 正式状态变化后需要重新合并，受影响的结果需要重新审阅 |

无论采用哪种方式，都不能以审阅过的旧结果覆盖后来发生的更新。首期可以选择较简单的全库版本校验；能否只校验受影响范围，需要另外定义依赖关系。

如果采用冻结窗口，冻结必须由 host 控制所有相关写入入口，包括正文、目录和附件。仅暂停客户端界面或网络广播，无法构成一致的冻结边界。在途输入要么在边界前接受并计入 `H`，要么明确拒绝并让客户端保留恢复材料。

冻结还需要明确持有者、超时、取消和异常退出后的恢复方式。普通文件系统不自动提供全 Vault 事务，也未必能阻止外部程序修改；外部变更必须纳入检测与重新校验。保存失败时不能宣布已经取得可发布的磁盘基线，部分写入后的恢复也不能依赖一次批量复制天然原子。

## 8. Patch 覆盖的是 Vault 变更

统一工作流不要求所有内容使用同一种差异编码。文本可以使用标准 unified diff，完整的 Vault 变更还需要覆盖其他内容：

| 对象                       | 所需表示                                           |
| -------------------------- | -------------------------------------------------- |
| 文本文件                   | 内容差异、基线内容校验与目标内容校验               |
| 文件和目录                 | 创建、删除、移动、重命名等变化及其前置条件         |
| 图片、字体和其他二进制附件 | 新内容字节，或接收方能取得并验证的不可变 blob 引用 |

文本 patch 不能独自携带所有附件变化。完整交付可以采用带 manifest 和 blobs 的变更包，或选择支持这些能力的既有格式；是否仍使用 `.patch` 扩展名尚未决定。重命名是否显式保留身份、空目录是否属于快照，也需要在格式中说明。

更新包至少标明来源基线和目标快照；提交包标明来源基线，以及可以验证的本地修改结果。服务端须能恢复合并涉及的基线内容，或由提交者补充可验证的基线材料。版本标识负责定位与校验，不替代内容本身。

目录结构即使将来由 Loro 管理，也不会自动解决 blob 存储问题。文件系统、对象存储或其他后端仍可按需承载附件；可迁移的引用应绑定内容或版本，不能仅依赖某台机器上的可变路径。

## 9. CRDT 与持久化边界

这套离线工作流提交的是两个快照之间的净变化。它会丢失原始编辑操作的身份、因果关系、作者信息和中间过程，不能当作原 CRDT 历史继续导入。批量传输 CRDT 增量则可以保留这些信息；batch 和内容 diff 不是同一回事。

例如，从 `ab` 出发，删除原来的 `b` 后再插入一个新的 `b`，最终文本没有变化，内容 diff 为空；CRDT 中旧字符和新字符却有不同身份。另一方同时删除原来的 `b` 时，两种历史可能得到不同结果。选择快照 / patch，是选择按最终文件状态合并的工作语义。

本阶段不做 CRDT 离线编辑，不自动意味着可以删除 host 的 CRDT 持久化。持久化还影响宿主重启、已确认但尚未写回普通文件的编辑、撤销和恢复。若后续选择只在内存维持在线历史，就需要另行决定草稿恢复机制、可能丢失的数据范围，以及重启后建立新历史并重新接入的规则。宿主内存接受、持久化完成和普通文件保存仍应分别表达。

快照基线也有自己的保存需求。即使不保存长期 CRDT 操作历史，离线更新与三方合并仍需要可恢复的文件版本；这不要求服务端永久保存所有版本，但需要明确保留期与过期后的处理流程。

关于 `EditorCore` 的讨论也尚未落定到 crate 拆分：它可以管理整个 Vault 的逻辑状态，同时让文档和附件按需加载。正文 CRDT、目录操作、普通内容 IO、历史持久化、快照导出与合并发布应有清楚边界；「管理整个 Vault」不要求所有字节常驻内存，也不直接决定持久化编排必须位于哪个类型。纯内存模型加 wrapper、接口名称和 wrapper 所属 crate 都留待后续确定。

## 10. 后续需要确定的事项

- 是否采用快照 / patch 作为离线工作流，以及下载、更新、提交的交互与工具形式。
- 快照基线由谁保存、保留多久，基线过期时如何补充材料或重新建立工作副本。
- 更新和提交的格式：文本工具的兼容性、附件传输、路径与文件身份、空目录及删除 / 重命名的表示。
- 本地基线元数据如何保存，以及应用更新中断或冲突时如何保持基线与工作目录一致。
- 采用全程冻结合并窗口，还是独立合并工作区加发布时校验；相应的取消、超时和失败恢复规则。
- host 接受、持久化与普通文件保存各自提供什么保证，是否继续保存在线 CRDT 历史。
- 正式发布如何更新活动 CRDT、撤销和客户端会话，以及跨文件部分写入后的恢复方式。

具体实施阶段与完成标准，在这些边界确定后再进入路线图。
